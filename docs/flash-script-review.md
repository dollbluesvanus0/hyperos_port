# Проверка скриптов прошивки — 2026-10-05

Проверены `bin/flash/mac_linux_flash_script.sh`, `bin/flash/windows_flash_script.bat`, `bin/flash/update-binary` и генерация этих файлов в `port.sh`. Проверка основана на коммите `712ec39`; эти шаблоны используются при `pack_method=super`. В режиме `aosp` используется другой установщик. Ни одна команда не выполнялась на телефоне.

## Ошибки, которые нужно исправить перед прошивкой

1. **P1 — Ошибки записи не останавливают установку.** В mac/Linux после `fastboot flash` отсутствуют проверки статуса; Windows также продолжает выполнение после ошибок `fastboot.exe`. В recovery функции `package_extract_file` и `package_extract_zstd` не вызывают остановку при ошибках, а скрипт заканчивается `exit 0`. На заглушке все команды `flash` возвращали 9, но mac/Linux всё равно сообщал `Flash completed` и возвращал 0. Ошибка `unzip` с кодом 7 также не препятствовала дальнейшему выполнению recovery. Нужны обязательные проверки каждой записи/распаковки и остановка до `set_active` и перезагрузки.
   Источники: mac/Linux строки 132–174; Windows 104–149; update-binary 10–18 и 163.

2. **P1 — Неверные разделы `boot_ab` и `dtbo_ab`.** Mac/Linux пишет в эти буквальные имена. Для A/B нужно писать в `boot_a`/`boot_b`, `dtbo_a`/`dtbo_b` или использовать корректный выбор слотов fastboot. Это не сокращение для двух слотов. При генерации A-only `s/_a//g` превращает `boot_ab` в `bootb`, поэтому ломается и этот режим. Команды подтверждены на генерируемом шаблоне.
   Источники: mac/Linux 137–141; port.sh 1400–1405. Поведение слотов: [исходный код AOSP fastboot](https://android.googlesource.com/platform/system/core/+/refs/heads/main/fastboot/fastboot.cpp).

3. **P1 — Неверные команды recovery для payload-прошивок.** В A/B ветке генератора используются имена `firmware-update/modem_a` вместо существующего `firmware-update/modem.img`, а `${part}` в этой ветке не задаётся. Получаются пути `/dev/block/bootdevice/by-name/` без имени раздела либо со старым значением переменной. Воспроизведено также для vbmeta. Для A-only в payload-ветке recovery-команды firmware вообще не добавляются. Mac/Linux в обеих payload-ветках тоже не получает firmware-команд, которые получает Windows.
   Источники: port.sh 1445–1480, особенно 1468–1478.

4. **P1 — Стирание `super` до проверки всех файлов.** Mac/Linux выполняет `fastboot erase super`, не проверив наличие и читаемость `super.img`, boot и dtbo. При отсутствующем файле старая система уже стёрта, новая не записывается, но затем скрипт всё равно перезагружает телефон. Нужна полная предварительная проверка и исключение ненужного стирания.
   Источник: mac/Linux 132–143.

5. **P1 — Пункт меню неверно обещает сохранить `/data/media`.** В обоих настольных скриптах пункт 2 подписан как очистка без удаления `/data/media`, но выполняет `fastboot erase userdata` и `erase metadata`. Это стирание разделов, а не удаление отдельных каталогов. Обещание сохранения фотографий/внутреннего накопителя неверно.
   Источники: mac/Linux 29, 154–157; Windows 41, 133–136.

6. **P2 — В Windows проверяется старый `%errorlevel%`.** В блоке `if exist (...)` проценты раскрываются до выполнения `zstd.exe`. Воспроизведение: команда завершилась кодом 7, `%errorlevel%` остался 0, а `!errorlevel!` показывал 7; ошибка была проигнорирована. Использовать `if errorlevel 1` либо отложенное раскрытие.
   Источник: Windows 18–19.

7. **P2 — Пути зависят от текущего каталога и не заключены в кавычки.** Windows проверяет устройство через `fastboot` из PATH, хотя комплектный файл находится в `bin\windows\fastboot.exe`. Остальные относительные пути тоже зависят от места запуска, а `%~dp0...` без кавычек ломается в каталогах с пробелами. Mac/Linux также не переходит в каталог скрипта и ищет ROM в текущем каталоге. Требуются переход в каталог пакета, единый путь к fastboot и кавычки.
   Источники: Windows 18, 57, 104–128; mac/Linux 80–90 и 136–143.

8. **P2 — `-s SERIAL` применяется только при проверке модели.** Последующие команды обоих скриптов не получают переданные аргументы fastboot. На заглушке `-s MOCK_SERIAL` присутствовал только у `getvar product`. При нескольких устройствах выбор телефона теряется. Все команды должны использовать один и тот же выбранный serial.
   Источники: mac/Linux 116 и 132–174; Windows 57 и 104–149.

9. **P2 — Несогласованный выбор кастомного boot.** Windows обещает выбор 1 по умолчанию, но при Enter `kernel` остаётся пустым и выбирается `boot_noksu.img`. Генератор без отдельного NoKSU-файла кладёт `boot_official.img`, поэтому такой сценарий обращается к отсутствующему файлу. В ветке `boot_custom.img` дополнительно опечатка `custom_botimg_file`, а блок штатного boot не удаляется. Нужны согласованные имена, явное значение по умолчанию и один выбранный boot.
   Источники: Windows 94–121; port.sh 1496–1535.

10. **P2 — Recovery удаляет весь `/tmp`.** Команда `rm -rf /tmp` выполняется до проверки модели и целостности ROM и может удалить файлы других компонентов recovery. Нужен собственный временный каталог и очистка только его содержимого.
    Источник: update-binary 66–69.

11. **P2 — Несовместимые способы выбора кастомного boot.** Mac/Linux выбирает кастомный boot по наличию файла, а recovery — по подстроке `ROOT` в имени ZIP. Генератор добавляет `ROOT` для EROFS, но не для EXT4 с KSU. Один пакет может прошиваться разными ядрами в зависимости от способа установки. Выбор должен задаваться метаданными пакета или одинаковой логикой установщиков.
    Источники: mac/Linux 136; update-binary 114; port.sh 1552–1556.

12. **P2 — Homebrew запускается через sudo.** При отсутствии fastboot/zstd mac-скрипт вызывает `sudo brew install ...`; Homebrew выполняет установку от владельца, а не через sudo ([официальный FAQ](https://docs.brew.sh/FAQ#why-does-homebrew-say-sudo-is-bad)). Кроме того, наличие команд определяется через англоязычный вывод `type`, который зависит от локали. Использовать `command -v`, корректную установку и проверку её результата.
    Источники: mac/Linux 33–43 и 61–67.

## Проверки

- `bash -n` прошёл для mac/Linux и обеих версий update-binary. Это подтверждает только синтаксис Bash; совместимость с конкретным `/sbin/sh` recovery требует отдельной проверки.
- Временный стенд `tmp/flash-review/reproduce.sh` использовал shell-функции вместо fastboot, zstd и других инструментов, обычные файлы вместо разделов. Подтвердил игнорирование ошибок записи, потерю serial, неверные A-only имена и команды генератора.
- Стенд `tmp/flash-review/errorlevel.bat` подтвердил раскрытие `%errorlevel%` до выполнения вложенной команды.
- Прошивочные шаблоны в рамках этой проверки не изменялись.
